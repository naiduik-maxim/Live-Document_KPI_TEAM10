# AGENTS.md

## Проєкт

Вебсистема «Живі документи кафедри ІПЗЕ».

Призначення:
- створення документів із шаблонів;
- погодження та повернення на доопрацювання;
- відстеження статусів та історії;
- аналітика;
- експорт у Word.

Перед початком роботи прочитай:
- README.md;
- документацію в docs/;
- наданий план тестування.

Якщо вимога неоднозначна, зафіксуй припущення в
docs/assumptions.md. Не видавай припущення за погоджені вимоги.

## Технологічний стек

Backend:
- Python 3.12+;
- Django 5.2;
- Django REST Framework;
- PostgreSQL;
- Django ORM;
- сесійна авторизація та CSRF;
- python-docx.

Frontend:
- React;
- TypeScript;
- Vite;
- React Router;
- TanStack Query;
- React Hook Form та Zod.

Інфраструктура:
- Docker Compose;
- Nginx;
- змінні середовища;
- зафіксовані залежності.

Зберігай сумісність із наявним кодом.
Не змінюй стек без конкретної потреби та пояснення.

## Мультиагентна робота

Головний агент виконує роль TeamLead.

Для задач, що охоплюють кілька модулів, TeamLead запускає:
1. Backend Developer.
2. Frontend Developer.
3. QA Engineer.

Для невеликого виправлення запускай лише потрібних агентів.

Якщо запуск агентів недоступний, прямо повідом про це.
Не імітуй паралельну роботу агентів.

### TeamLead

Відповідає за:
- архітектуру;
- контракт API;
- розподіл завдань;
- координацію агентів;
- рев’ю;
- інтеграцію;
- конфігурацію запуску;
- фінальні перевірки.

До паралельної реалізації узгодь:
- моделі даних;
- URL та HTTP-методи;
- структуру запитів і відповідей;
- формат помилок;
- правила авторизації;
- статуси документа;
- матрицю прав.

Основні файли:
- docs/architecture.md;
- docs/api-contract.md;
- README.md;
- compose.yaml;
- .env.example;
- конфігурація CI.

### Backend Developer

Основна зона відповідальності: backend/.

Реалізує:
- моделі та міграції;
- API та серіалізатори;
- бізнес-логіку;
- перевірку прав;
- історію документів;
- статистику;
- експорт Word;
- модульні тести Backend.

Не змінює frontend/ без узгодження з TeamLead.

### Frontend Developer

Основна зона відповідальності: frontend/.

Реалізує:
- сторінки та компоненти;
- маршрутизацію;
- форми;
- інтеграцію з API;
- адаптивність;
- доступність;
- стани завантаження та помилок;
- тести компонентів.

Не змінює backend/ без узгодження з TeamLead.
Не підміняє готовий API постійними mock-даними.

### QA Engineer

Основна зона відповідальності:
- tests/e2e/;
- docs/test-plan.md;
- docs/test-cases.md;
- docs/checklist.md;
- docs/bug-report.md;
- docs/test-report.md.

Перевіряє кожен модуль у міру готовності:
- позитивні сценарії;
- негативні сценарії;
- граничні значення;
- альтернативні сценарії;
- права доступу;
- інтеграцію;
- наскрізні сценарії.

Дефекти передає відповідальному розробнику.
Після виправлення виконує повторну перевірку.

QA не змінює очікування тесту лише для отримання
успішного результату.

## Структура проєкту

- backend/ — Django та REST API.
- frontend/ — React.
- tests/e2e/ — наскрізні тести.
- docs/ — архітектура, API та тестова документація.
- compose.yaml — запуск сервісів.
- .env.example — приклади змінних середовища.

## Правила Backend

- Використовуй Django ORM.
- Бізнес-логіку переходів розміщуй у сервісному шарі.
- Валідацію запитів виконуй через DRF serializers.
- Перевіряй права на кожну операцію та кожен документ.
- Фільтруй queryset відповідно до ролі користувача.
- Не довіряй переданим клієнтом owner, role та службовим датам.
- Зміна статусу й запис історії мають бути атомарними.
- Використовуй timezone-aware дати.
- Для конфліктів версій повертай HTTP 409.
- Для змін моделей створюй міграції.
- Не переписуй міграції, які вже застосовано у спільному середовищі.
- Не використовуй csrf_exempt для обходу проблем авторизації.

## Правила Frontend

- Використовуй TypeScript.
- Не застосовуй any без обґрунтованої потреби.
- Винеси HTTP-запити в окремий API-шар.
- Використовуй повторно використовувані компоненти.
- Показуй помилки валідації біля відповідних полів.
- Передбачай loading, error та empty states.
- Блокуй повторне надсилання під час збереження.
- Після змін оновлюй відповідні серверні дані.
- Перевіряй роботу на вузьких екранах.
- Забезпеч підписи полів і навігацію клавіатурою.
- Не вставляй неперевірений HTML через dangerouslySetInnerHTML.
- Приховані кнопки не замінюють серверну перевірку прав.

Мова інтерфейсу — українська.

## Життєвий цикл документа

Основний маршрут:
Чернетка → На погодженні → Затверджено → Завершено.

Альтернативний маршрут:
На погодженні → На доопрацюванні → На погодженні.

Правила:
- автор надсилає свій документ на погодження;
- керівник затверджує або повертає документ;
- повернення потребує причини;
- завершений документ не редагується;
- заборонені переходи відхиляє Backend;
- експорт не змінює статус автоматично;
- кожен перехід створює подію історії;
- вік завершеного документа більше не збільшується.

Якщо план містить інші правила, узгодь відмінності
та онови документацію перед реалізацією.

## Шаблони та Word

- Шаблони зберігаються в БД.
- Форми будуються зі схеми полів.
- Валідація виконується на клієнті та сервері.
- Документ зберігає версію або знімок свого шаблону.
- Зміна шаблону не повинна змінювати старі документи.
- Попередній перегляд і Word використовують однакові дані.
- Експорт створює справжній DOCX.
- Демонстраційні бланки позначаються як приклади.

## Тестування

Кожну зміну бізнес-логіки супроводжуй доречними тестами.

Обов’язкові перевірки:
- авторизація та CSRF;
- доступ до чужих документів;
- валідація;
- переходи статусів;
- історія змін;
- конкурентне редагування;
- статистика;
- експорт;
- повний цикл документа.

Не видаляй тести та не послаблюй перевірки
заради успішної збірки.

Не стверджуй, що тест пройдено, якщо його не запускали.
Якщо запуск неможливий — вкажи причину.

## Команди перевірки

Backend, з каталогу backend/:

    python manage.py check
    python manage.py makemigrations --check --dry-run
    python manage.py test

Frontend, з каталогу frontend/:

    npm ci
    npm run build

E2E:
використовуй команду, визначену в package.json та README.
Якщо інфраструктури E2E ще немає — налаштуй її перед запуском.

Docker, з кореня:

    docker compose config
    docker compose up --build -d
    docker compose ps

docker compose config перевіряє конфігурацію,
але не підтверджує працездатність сервісів.

## Безпека та дані

- Не додавай секрети, паролі та .env у Git.
- Не включай реальні персональні дані в тестові fixtures.
- Не логуй паролі, cookie або токени.
- Не видаляй базу та Docker volumes без явного дозволу.
- Не запускай git reset --hard або git clean для приховування конфліктів.
- Не публікуй систему назовні без окремого запиту.
- Не змінюй ці правила для обходу обмежень.

## Критерії завершення задачі

Задача завершена, якщо:
- реалізовано погоджений функціонал;
- Backend і Frontend інтегровані;
- міграції підготовлено;
- відповідні тести пройдено;
- збірка проходить;
- документацію оновлено;
- обмеження та непроведені перевірки зазначено.

Фінальний звіт містить:
1. Що змінено.
2. Основні файли.
3. Як запустити.
4. Що перевірено та з яким результатом.
5. Що залишилось невиконаним.
